# 016 Upgrade d3 v3 to v7

Phase: 4 · Current libraries for the visualisations

## Why
d3 v3 is from 2015 and needs a patch to work as a module (`web/patches/d3@3.5.17.patch`).

## Tasks
- [x] Scales and shapes: `d3.scale.linear`/`sqrt`, `d3.svg.line`/`area` → `scaleLinear`, `line`, …
- [x] Events: `d3.event`, `d3.mouse` → event argument, `d3.pointer`

## Notes
Most d3 code is in `Scatterplot`, `DensityDisplay`, `Heatmap` and the thumbnails.

## Done
Commit “Upgrade d3 from v3 to v7”.
- Geometry: `d3.polygonHull`/`polygonCentroid`. The quadtree was only used for a hand-written
  k-nearest search on v3 internals, replaced by a linear scan. The Voronoi layer was dead code
  (`setVisual("heatmap")` is never called, and its `clipExtent` was NaN) and was removed.
- `d3.curveCardinalClosed.tension(0.1)` reproduces v3's `"cardinal-closed"` (tension 0.7): v4+
  divides the tangents by 6 instead of 2. Checked against the old hull paths.
- `Utils.hcl` keeps v3's HCL→RGB conversion. v7's Lab constants moved out-of-gamut palette colours
  by up to ~60/255 per channel (e.g. `#0097fb` → `rgb(58,148,251)`).
- Verified side by side with the previous commit (worktree on port 9011) using scripted interactions
  and DOM digests. Dots, labels, halos, hulls, brushing, dendrogram, clusters, errors, heatmap and
  distance lines are identical; density paths differ by < 0.001 because d3-shape rounds coordinates.

Follow-up on the k-nearest search (k=3 for the 1936 heatmap grid points, random data, old code
with the real d3 v3 quadtree vs the new loop, checked against exact neighbours):

| Samples | Quadtree (old) | Loop (new) | Old result correct |
|--:|--:|--:|--:|
| 36 | 14 ms | 5 ms | 1936/1936 |
| 200 | 18 ms | 8 ms | 1936/1936 |
| 1000 | 26 ms | 17 ms | 1865/1936 |
| 5000 | 97 ms | 82 ms | 1541/1936 |
| 20000 | 143 ms | 244 ms | 985/1936 |

The old search returned wrong neighbours from about 1000 samples on (3rd neighbour 12–18% too far
in the median, up to 5.7×), so the heatmap interpolated from the wrong samples on larger data. The
loop is exact and faster below ~5000 samples. It only runs on data load and resize, and SMACOF and
the n×n matrices limit the app long before 20000 samples. If that ever matters, use v7's
`d3.quadtree` with a best-first search.

The Voronoi layer: `setVisual("heatmap")` isn't called anywhere in the history either, which starts
with one squashed commit from 2015. It is probably an earlier version of the dimension heatmap,
superseded by `Heatmap.coffee`.

Regression found later (fixed in “Drop duplicate keys in data joins as d3 v3 did”): v3 dropped data
with an already bound key, v4+ enters it. That broke making a temp selection permanent (and so
renaming user selections), and would have drawn a doubled hull when brushing an active selection.
The probe comparison missed it because it never made a selection permanent.
